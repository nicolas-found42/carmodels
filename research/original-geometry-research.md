# Ford Racing 2 original car geometry and texture recovery

Research snapshot: 2026-10-04. Scope: identify what original vehicle geometry and textures are already recoverable from the PAL PS2 data, what is only a hypothesis, which prior notes are superseded, and the shortest evidence-backed route to original per-car models. The original silhouette gallery remains available. The new recovered.html inspector and all-car GLBs add original-coordinate, textured assembly candidates; see original-recovery.md for the later experiments and limitations.

## Findings

The 35 per-car `.PS2;1` files themselves contain the `0x34` geometry-record table, geometry headers, and aligned payload planes after the name and texture sections. They also contain a name tree and texture library; there is no primary evidence that their vertex positions must come from a separate shared pool. `3DDATA/misc.ps2;1` has a `GENERIC_CAR` name, but remains a separate unverified resource lead. The current best direct evidence for car positions comes from the six-byte planes in each car's own file and their per-record bounds relationship described below. [Carmodel format notes](format-notes.md), [section parser](../tools/ps2_sections.py), [geometry VIF contract](../.scratch/inputs/notes/evidence/fr2-geometry-vif-contract/README.md)

The best original-data starting points are the exact PAL executable `SLES_517.05` (SHA-256 `216711210898aee296eed73d0776e7f733bac04c334002683bce769c86beea95`), the archive-pinned `.PS2;1` model files, and `3DDATA/misc.ps2;1`. The latter is 236,944 bytes and has a `GENERIC_CAR` name; it is a lead, not yet established as the vertex pool. Per-car manifests under `reference/ford/cars/` pin each copied model and livery file with hashes. The corpus overview records 35 vehicle entries and their exact file relationships. [Ford corpus index](../reference/ford/README.md), [model container format notes](format-notes.md), [static recovery source identity](../.scratch/inputs/notes/evidence/fr2-static-recovery/README.md)

An older topology interpretation is withdrawn. The historical index-like byte ranges cited for G_TORINO, F100, and Taurus are wholly inside the palette block region reported by the current texture parser: G_TORINO `[1748,6410)` is within palette bytes `[720,17168)`, F100_56 `[1876,3930)` within `[848,29584)`, and TAURUSA `[2196,4250)` within `[1168,53456)`. Those bytes are palette data, not proven triangle-strip topology. The prior claims of 1,016 shared wheel/hub triangles, three Ford GT body strips, and 917 body triangles are therefore invalid. The files do contain named part strings, palettes, image planes, and transform-like tail records, but the part-to-geometry/topology relation remains open. [Parser source](../tools/ps2_container.py), [palette-zone checks in the experiment receipt](evidence/original-recovery/geometry-experiment/results.json), [older format notes, superseded in this paragraph](format-notes.md)

The geometry table carries two group counts per `0x34` record at offsets `+0x1c` and `+0x28`, followed by flag/count-dependent headers and aligned payload planes. In the 35 car files, the corrected parser finds 1,872 records, 12,080 headers, and 657,139 six-byte records, with nonempty six-byte data in 1,837 geometry records (the first record in each file is empty). For the full 56-file corpus, the bounded section chain reaches exact EOF; 54 use the current loader's 68-byte later header and two match a measured 60-byte legacy profile whose use by this executable is not shown. Three ordered bound pairs are stored at `+4/+8`, `+12/+16`, and `+20/+24`. Their relationship to the six-byte data is no longer merely unknown: the experiment below matches every nonempty car record to those bounds using the VU path's per-axis max-absolute extent and 1/16384 normalization. The raw table and code layout are described in [the parser](../tools/ps2_sections.py), [geometry endpoint audit](../.scratch/inputs/notes/evidence/fr2-geometry-endpoints/README.md), and [geometry VIF contract](../.scratch/inputs/notes/evidence/fr2-geometry-vif-contract/README.md)

### Car-specific signed-six-byte position experiment

I persisted a reproducible, read-only parser/measurement script and source-hashed JSON receipt under [geometry-experiment](evidence/original-recovery/geometry-experiment/run_geometry_experiment.py). It uses the parser's actual count fields at offsets `+0x1c` and `+0x28`, the 35 `3DDATA/CARS/*.PS2;1` files, and pinned hashes for every input. It combines the six-byte planes from both groups within each record, decodes the triplets as signed little-endian 16-bit values, and compares per-axis extrema against the record's serialized bounds. This is a real per-car local geometry payload path; no external/shared geometry pool assumption is needed for this coordinate evidence.

Reproduce from the carmodels root with the existing Python environment:

```sh
python3 research/evidence/original-recovery/geometry-experiment/run_geometry_experiment.py \
  --data-root ../.scratch/inputs/games/ford-racing-2/extracted/files/3DDATA/CARS \
  --tools-root ../tools \
  --output research/evidence/original-recovery/geometry-experiment/results.json
```

The data fits the traced VU path unusually tightly. For each record and axis, compute `extent = max(abs(bbox_min), abs(bbox_max))` and map each signed component as `raw / 16384 * extent`. All 1,837 records with six-byte data have both mapped endpoints on all three axes within one quantization step (`extent / 16384 + 1e-6`) of the serialized bbox endpoints: 1,837/1,837. Across 11,022 endpoint comparisons, the largest residual is 0.9998 of a quantization step; the mean is 0.2467 steps. The signed data also uses `-16384` or `+16384` extrema frequently (3,956 and 3,996 endpoint occurrences respectively). Independently, for every one of the 1,971,417 signed component words, `reinterpret_float32(0x44400000 + sign_extended_raw) - 768.0` equals `raw / 16384` with maximum measured error 0.0. This directly matches the code path: `FUN_001288b0` builds the qword4 per-axis max-absolute bbox vector; `FUN_00128e88` emits STROW 768 and STMOD 1 before the V3-16 REF; VU overlay 5 subtracts 768 from `vf15.xyz` then multiplies by qword4 loaded as `vf20`. This evidence strongly supports the six-byte triplets as normalized local position input to the VU transform, and shows the coordinate normalization is per-record, not one global scale. It is static source plus corpus arithmetic, not proof of final rendered output or hardware behavior. [Per-record validation receipt](evidence/original-recovery/geometry-experiment/results.json), [VIF writer contract](../.scratch/inputs/notes/evidence/fr2-geometry-vif-contract/README.md), [corrected VIF row/mode order](../.scratch/inputs/notes/evidence/fr2-geometry-vif-preamble/README.md), [VU instruction trace](../.scratch/inputs/notes/evidence/fr2-geometry-vu-dispatch/README.md)

The measurement also tested alternative local `center + raw / 32767 * half_extent` and `/16384 * half_extent` forms. These enclose all records by construction but match both bbox endpoints within one local quantization step on zero and 383 records respectively; they are weaker than the observed maxabs `/16384` model. A pooled single-scale affine fit across all records has low R² (0.47, 0.52, 0.39 by axis), and fixed shared scale/bias candidates do not match. Those earlier-style global hypotheses are falsified by car/record-local scaling, not by the local position mapping. The durable result records the fixed-scale grid and all per-record residuals. An initial exploratory script read the second group count from `+0x1e` by mistake; all conclusions from that version are withdrawn. The persisted script reads the two real fields separately at `+0x1c` and `+0x28`.

An adjacent loader path has been mapped accurately after correcting an earlier four-byte error: four serialized binary32 fields at row offsets `+8/+12/+16/+20` map to runtime offsets `+12/+16/+20/+24`, then feed a VU0 transform helper. The correction is established by deterministic cursor arithmetic and a corpus-bound check across 28,453 rows and 113,812 words. This row is a named-object transform input path; it is not the six-/four-byte geometry payload, and does not supply mesh vertices or prove the rendered transform output. The old mapping and its supportive Jev receipts remain superseded. [Correction and disposition](../.scratch/inputs/notes/evidence/fr2-geometry-consumer-audit/root-correction/README.md), [current source-to-consumer trace](../.scratch/inputs/notes/evidence/fr2-geometry-consumer-audit/object-float-provenance-01.md)

The packet writer's source arguments directly connect the geometry record count/payload pointers to V3-16, V4-8, and optional V2-16 REF transfers. V3-16 uses a 6-byte-per-count source span, and the writer emits STROW `0x44400000` (float 768) followed by STMOD 1 before that V3-16 command. Thus the candidate signed triplets enter the exact transfer whose row-add bit pattern the VU later removes. V4-8 is emitted before that STROW/STMOD pair, so its effective incoming mode/row remains a separate open question; optional V2-16 has its own STROW 6144 and STMOD 1 sequence. A separate packet emits an eight-qword V4-32 transfer (first four from a caller block, last four from four producer-traced scratchpad vectors) and MSCAL `0x5cc`. The geometry writer's five-qword TOPS-relative V4-32 header has selector `0x208` or `0x2c8` in qword 3 Z; the resumed VU reads `TOP+3.z` into `vi03`, which bases subsequent VU data loads. The TOPS linkage remains conditional on actual DMA order/initial state; these selector values are not assigned as XGKICK pointers. [VIF contract](../.scratch/inputs/notes/evidence/fr2-geometry-vif-contract/README.md), [VU dispatch](../.scratch/inputs/notes/evidence/fr2-geometry-vu-dispatch/README.md), [VIF preamble corrections](../.scratch/inputs/notes/evidence/fr2-geometry-vif-preamble/README.md), [VU consumer and lane mapping](../.scratch/inputs/notes/evidence/fr2-geometry-vu-consumer/README.md)

Texture recovery is considerably further along than the older `format-notes.md` summary suggests. The static model upload path and GS address tables have been used to decode level-zero images across all 2,370 texture records in the 56-model baseline: 350 format 1, 1,551 format 3, and 469 format 4. This includes 2,020 index planes, CLUT handling, indexed swizzle/address mapping, and 19 format-4 records with 256-entry palette blocks. The complete level-zero image hashes and source identities are retained. Therefore the earlier statement that texture page extents and palette mapping were unresolved is obsolete for this bounded level-zero path; decoded pixels still lack demonstrated in-game renderer equivalence. [Level-zero texture upload audit](../.scratch/inputs/notes/evidence/fr2-texture-upload-audit/README.md), [current static recovery summary](../.scratch/inputs/notes/evidence/fr2-static-recovery/README.md)

Mip handling is partly recovered. The loader reads the count, allocates levels, halves dimensions, and uploads up to three extra levels; the corpus uses at most two. Across all 56 files, 2,370 texture records contain 4,941 levels (2,571 extra), and source-plane bytes equal computed transfer bytes for 79,708,000 bytes. Mip record fields at `+0/+2/+4/+8/+12` have bounded source/allocation/TBW/DBW relationships, but `+6` and `+14` and runtime allocation/base state remain open. A conditional address-set experiment found 75 packed logical 8x8 mip records (53 format 3, 22 format 4) where 32 of 64 sampled pixel starts fall outside addresses written under the assumed transfer state. This is not evidence of game corruption; it marks a concrete unresolved state or address-model question. Mip pixels, full level selection, runtime CLUT transitions, UVs, and final material assignments remain unproven. [Mip upload audit](../.scratch/inputs/notes/evidence/fr2-texture-upload-audit/mip-upload-static-audit/README.md), [mip field and address audit](../.scratch/inputs/notes/evidence/fr2-texture-mip-field-audit/README.md)

## What is still missing for original per-car meshes

The strongest closed geometry chain is `per-car six-byte signed triplets -> V3-16 with STMOD1 and row 768 -> normalized local XYZ -> per-record maxabs scale -> VU transform -> FTOI4/store -> XGKICK`. Overlay 6's continuation stores three output qwords and executes `XGKICK vi11` at pair 17; this corrects the earlier narrow statement that overlay 5 has no XGKICK after its E-stop. The saved [overlay-5 assembly](<../.scratch/inputs/.scratch/evidence/vu/private-work-016dac24781c4c9ea7c99aa0fa79c310/overlay-5.s>) and [overlay-6 assembly](<../.scratch/inputs/.scratch/evidence/vu/private-work-016dac24781c4c9ea7c99aa0fa79c310/overlay-6.s>) support this sequence. The remaining join is `named part -> which local geometry record(s) -> primitive/index ordering and attribute lanes -> draw`. Current evidence has not identified:

- the semantics of four-byte and twenty-byte planes, the optional V2-16 data, and the separate V4-8 lane; V4-8 may encode packed attributes such as color or normals, but this has not been proved;
- how named per-car parts select local geometry records and how triangles/strip order are represented; historical strip-index zones were actually palette bytes;
- what additional per-vertex data, if any, is stored in the 20-byte plane and how its fields are used;
- the final world coordinate axes, object origin, winding, strip restart behavior, and any local transform needed after the recovered normalization;
- original UV encoding, UV-to-texture index linkage, palette/texture/material assignment, alpha behavior, or mip selection;
- whether normal vectors are serialized, packed, generated, or transformed by VU code;
- wheel/body mesh combination, duplicates, LODs, collision-only or animation records, and the render draw boundary;
- any actual runtime capture proving DMA queue order, VIF state, VU memory contents, XGKICK/GIF submission, or final image.

## Recommended recovery sequence

1. Keep the established 35-car six-byte coordinate extraction and source-byte provenance. Extend the receipt with negative mutations of the source plane count, V3-16 REF pointer, STROW value, and maxabs qword source; each must break the expected bbox relation without mutating original assets.
2. Trace the per-car part/name records to the specific `0x34` geometry records and identify the four-byte, twenty-byte, and header fields consumed for non-position attributes or primitive/index control.
3. Continue the `0x5cc` VU trace through overlay 6. It converts the output with FTOI4, stores three qwords per output vertex, updates integer state, and executes `XGKICK vi11` in the continuation. Determine which stored lanes carry UV, color, and position from the exact producer inputs and downstream GIF interpretation.
4. Reconcile VU geometry construction with the container's strip/primitive representation. Historical index-like ranges must not be reused: they fall inside parsed palette regions. Run count, ordering, and max-index checks only after actual primitive/index semantics are established.
5. Derive a typed extractor only after at least one source-to-draw chain closes. Keep planes named by offsets initially; assert vertex index maxima below the corresponding recovered vertex count, finite decoded coordinates, bounds consistent with the serialized endpoint table, and texture references inside the recovered library. Add negative and boundary cases, then run the extractor over the hash-pinned corpus.
6. Export one test model to OBJ/GLB with the decoded texture/UV/material linkage. Compare it with an owner-observed in-game reference if available; label that review as visual corroboration, not proof. Expand to all car models only after the witness passes deterministic byte/count checks.

The per-car files already contain recoverable local position inputs, so the next work should focus on linking those records to named parts and decoding their primitive/attribute organization. `misc.ps2;1` remains worth investigating for shared or generic assets, but it should not be treated as the required position source. If static source cannot settle draw selection or material behavior, compare against a safe original GS/VU capture; the current work has not observed actual hardware or emulator rendering.

## Source notes and provenance

All local citations above point to primary project artifacts: archive-pinned model/parser results, saved executable/overlay traces, and source-matched VIF/GS implementation audits. Jev results in those bundles are advisory; deterministic instruction/byte and archive-hash checks resolve known conflicts. The source notes preserve non-auto review/escalation outcomes and old hypotheses rather than rewriting them. In particular, the four-byte object-row mapping, geometry endpoints initially treated as triplets, initial VIF E-pair numbers, VIF BASE/OFFSET ordering, `0010f8f8` data interpreted as a DMA REF, and a single global geometry scale are corrected or rejected. The per-record `raw/16384 * maxabs_bbox` mapping is independently supported by the persisted car-corpus experiment here.
