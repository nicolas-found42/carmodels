# Midnight Club 3 Remix PS2 preview decoder research

This investigation supplies primary implementation leads for PS2 VIF decoding and related Angel part transforms. It does not establish a public parser for the supplied retail Remix PCK geometry wrapper, nor claim that any of the 94 source packages has been rendered. Executable analysis and conversion belong to the separate decoder work. The retained [preview-readiness investigation](midnight-club-3-remix-preview-readiness.md) remains the source for the existing native corpus observations; its probe was reused, not rerun here.

## Sources that can guide the decoder

The strongest exact implementation is [PCSX2 Vif_Unpack.cpp](https://github.com/PCSX2/pcsx2/blob/master/pcsx2/Vif_Unpack.cpp). The complementary [ps2sdk packet2_vif.h](https://github.com/ps2dev/ps2sdk/blob/master/ee/packet2/include/packet2_vif.h) constructs VIF packets and documents their addressing and unpack controls. Their fetched code and screening receipts are retained in [followup-calls.json](evidence/midnight-club-3-remix/previews/research/followup-calls.json) and [implementation-calls.json](evidence/midnight-club-3-remix/previews/research/implementation-calls.json). These are fetched snapshots of mutable branches, not pinned game-version sources. PCSX2 carries GPL-3.0+ and the ps2sdk header carries Academic Free License 2.0; preserve provenance and review license requirements if code is copied.

| Field or behavior | Primary-source implementation |
| --- | --- |
| Command word | ps2sdk builds immediate in bits 0–15, NUM in bits 16–23, CMD in bits 24–30 and IRQ in bit 31. |
| UNPACK immediate | ps2sdk combines the VU address, unsigned bit 14 and double-buffer bit 15. The address is measured in 16-byte units. |
| UNPACK command | ps2sdk combines the mode with masked bit 4 and command base 0x60. |
| NUM | PCSX2 interprets encoded zero as 256 vectors. |
| Destination | For VIF1, FLG bit 15 adds TOPS; the destination byte address is then shifted by four and masked to VU memory. |
| Source widths | PCSX2 has S32/S16/S8 widths 4/2/1; V2 widths 8/4/2; V3 widths 12/6/3; V4 widths 16/8/4; V4-5 uses two bytes. |
| Cycle behavior | STCYCL fill and skip modes change the number of source vectors consumed and destinations written. A WL field of zero represents 256. |
| Output values | USN controls sign extension. Masks select source data, row, column or write protection; STMOD can add or update row values. |
| Hardware details | V3 writes can overlap the following source value for W; V2 replicates X/Y; packed V4-5 has its own component expansion and ignores normal mode behavior. |

The implementation should parse a validated stream boundary and maintain VIF state. A byte sequence that resembles an UNPACK command or finite XYZ data is not enough to identify a mesh. The resulting VU memory still needs the game-specific interpretation, primitive assembly and vehicle component transforms. [Source verification](evidence/midnight-club-3-remix/previews/research/source-verify.json) supports the command layout at confidence 0.98 and the stateful decoding limitation at 1.00.

The literal gh_grep search also found [naken_asm VIF constants](https://github.com/mikeakohn/naken_asm/blob/master/include/playstation2/vif.inc), including V3_32 0x68 and V3_16 0x69. This confirms useful command identifiers, not an MC3 wrapper or a vertex schema. The context-awesome PS2 SDK search was screened as irrelevant and contributes no format evidence.

## Part-transform and conversion leads

A screened gh_grep result for [AngelStudiosBlenderAddon import_modscene.py](https://github.com/Dummiesman/AngelStudiosBlenderAddon/blob/master/io_scene_angelstudios/import_modscene.py) imports .mod/.xmod objects and loads per-part geometry/name.mtx files. Its [utils.py](https://github.com/Dummiesman/AngelStudiosBlenderAddon/blob/master/io_scene_angelstudios/utils.py) reader consumes four groups of three little-endian floats: three basis vectors followed by translation. It assembles a 4x4 matrix, applies axis conversion and additional rotations before returning it. See the screened source in [transform-mod-calls.json](evidence/midnight-club-3-remix/previews/research/transform-mod-calls.json). This is a concrete related-engine implementation, but applying its coordinate conversion or file layout to MC3 PCK would be a hypothesis. No matching retail package table was checked against it.

The existing [TahmidAlam converter](https://github.com/TahmidAlam-git/MC3_extraction_tools/blob/main/mesh_to_obj.py) handles Xbox mesh.xbck/g.xbck, and the retained plain-mesh/TEX research concerns shared traffic files. Neither establishes decoding of the 94 retail PS2 vp_* packages. A Firecrawl Nexus result advertised a PS2 Silvia replacement mod; its page was screened as irrelevant to the parser question and was not consumed as conversion evidence. Likewise, full Angel addon and Varunda/ant pages were skipped. Search leads are not proof of a usable converter.

The bounded source-selection experiments used five candidates: PCSX2, ps2sdk, ordinary MC3 mesh research, the Xbox converter and the related Angel addon. [jev_find](evidence/midnight-club-3-remix/previews/research/vif-find.json) selected PCSX2 with probability 0.99 when asked for the exact VIF state machine. A separate [no-match experiment](evidence/midnight-club-3-remix/previews/research/pck-no-match-find.json) judged the existence of a validated retail PS2 PCK wrapper/transform implementation within those candidates at 0.07. Its forced top candidate is not an answer when existence is absent. [jev_rerank](evidence/midnight-club-3-remix/previews/research/source-rerank.json) placed PCSX2 and ps2sdk first at 0.85 and 0.75. These three experiments consumed 2,495 input and 270 output tokens. They measure judgments over this candidate set; there is no labeled extraction/render accuracy, individual latency or provider cost measurement in those receipts. They do not prove that no other converter exists.

## Live TypeSafe contract and application opportunities

The [live documentation index](https://docs.typesafe.ai/llms.txt), [question API](https://docs.typesafe.ai/sdk/python/api/types/questions), [response API](https://docs.typesafe.ai/sdk/python/api/types/responses), [primitives guide](https://docs.typesafe.ai/primitives), [composite scoring pattern](https://docs.typesafe.ai/patterns/composite_scoring) and [reranking cookbook](https://docs.typesafe.ai/cookbooks/rerank_typesafe) were fetched and screened. Retained batches include the complete fetched material and decisions. The general SDK usage page was skipped; the more specific question and response contracts were consumed after their own screening.

The current question API uses a non-null state, keyed questions, nonempty Choice option maps, ordered Score levels and Noul criteria for a single proposition. Choice returns option probabilities and confidence; Score returns a level distribution, expected score and confidence; Noul returns the probability of its stated proposition. Independent judgments can share one batch. Dependent questions require a later request with the earlier result added to the state.

Useful future application judgments concern selection among actual decoded components or preview variants, semantic catalog retrieval, texture/material candidate ranking, and evidence-backed labeling of an ambiguous part. Give each option its source identity and measured properties; include no_match. Use Choice for a defined selection, Noul for a stated proposition and Score for a described degree. Normalize and combine independent dimensions in code. Exact bounds, counts, hashes, packet rules and file writes stay deterministic. A judgment cannot provide missing vertices, validate an unsupported parser or turn an unrendered package into preview-ready.

Experiments should include stock versus customization parts, a misleading filename, absent textures, incomplete components, duplicate candidates and intentionally malformed input. Measure the actual selected part and resulting assembly against source-backed labels, as well as tokens, raw provider cost and end-to-end latency. The rerank cookbook recommends a deterministic shortlist followed by comparable judgments; omitted candidates remain unrecoverable. No asset-specific threshold is established by its legal-document benchmark.

The [official OpenRouter compatibility guide](https://docs.typesafe.ai/guides/providers/openrouter) specifies base_url https://openrouter.ai/api, with the SDK appending /v1/systemone, and the full Jev model alias. The live Python response schema defines Usage with only input_tokens/output_tokens and extra=ignore, while exposing raw_http_response. The guide's general extra-field compatibility wording must not be read as a promise of a typed usage.cost attribute. Retain provider cost from the raw JSON body when it is supplied. [jev_compare](evidence/midnight-club-3-remix/previews/research/provider-compare.json) flagged the typed-cost preservation reading as conflicting at confidence 0.97; the [verification](evidence/midnight-club-3-remix/previews/research/source-verify.json) supports the qualified raw-body recommendation at 0.98. Importing typesafe_sdk with the stock python3 in this research shell failed with ModuleNotFoundError; this does not contradict the application's previously retained successful configured SDK runs. No new application SDK request was run here.

## Evidence intake and limits

All external payloads were retained and screened before consumption. Pass material was used as task data. Review decisions were inspected under the Jev skill: Firecrawl agent_hints and documentation fetch/clipboard helpers were ignored as instructions, while separable technical content or URL metadata was retained. The inspections are in [screen-inspections.json](evidence/midnight-club-3-remix/previews/research/screen-inspections.json) and [its supplement](evidence/midnight-club-3-remix/previews/research/screen-inspections-supplement.json). Skipped pages/searches are not conversion evidence. No block recommendation was received.

This note does not modify production tools, source assets, catalogs or dealership models. It establishes neither PCK wrapper offsets nor material ownership, component placement, native render fidelity or a working preview for any package. Those claims require the executable-derived decoder, falsifiable corpus checks and actual assembled renders from the parallel implementation work.
