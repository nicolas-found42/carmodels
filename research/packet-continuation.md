# Original car packet continuation: VIF, VU, GIF, and GS

Snapshot: 2026-10-04. This continuation follows the existing source-pinned geometry work in [original-geometry-research.md](original-geometry-research.md) and its linked evidence. It reads source artifacts from the private input bundle but does not modify them. It combines pinned static exports and VU assembly with a byte-validated in-game PCSX2 save state and a complete one-frame GSDump decode. The GSDump supplies actual GS-bound GIF transfers; the save state supplies paused runtime memory. Neither alone traces a particular car object all the way to a particular GS draw.

## What the pinned packet sources establish

The saved EE path starts at `FUN_001288b0`. It emits a direct GIF/GS setup packet via `FUN_00129428`, computes per-record packet-plane offsets from each header, and calls `FUN_00128e88` with the count and three plane pointers. The first plane pointer is the six-byte-per-record source; the next is the four-byte-per-record source; the third is optional. The two geometry groups use separate record fields and pointers, as recorded in the earlier VIF contract.

For every call, `FUN_00128e88` writes a five-qword V4-32 packet at address zero with TOPS-relative addressing (`0x6c058000`). The selected value `0x208` or `0x2c8` is used as the V3-16 UNPACK ADDR, with V4-8 at ADDR+1 and optional V2-16 at ADDR+2; it is not the Z lane of the five-qword header. It then appends a V4-8 REF at selected base+1 from the four-byte source and a V3-16 REF at selected base from the six-byte source. If the optional pointer is nonzero, it appends a V2-16 REF at base+2. The writer puts STROW `0x44400000` and STMOD `1` before the V3-16 path, and STROW `0x45c00000` / STMOD `1` before the optional V2-16 path. These are exact source-level command constructions and parameter/pointer relationships; they do not assign data semantics to the four-byte or optional planes. See the generated [static trace receipt](evidence/packet-continuation/static-trace.json) and source pins in it.

The saved overlay-5 instructions capture TOP into `vi01`, load `TOP+3.z` into `vi03`, and then read VU data memory relative to `vi03`, including qwords at offsets 0 and 2 and W at offset 1. The continuation performs vector operations and an FTOI4 conversion. Overlay 6 converts `vf17.xyz` into `vf16.xyz`, stores `vf12`, `vf30`, and `vf16` in consecutive qwords, and later executes `XGKICK vi11`. The in-game state has VIF1 CYCLE=`0x404`, MODE=`0`, BASE/TOPS=`0x388`, TOP=`0x3aa`; the overlay-5 image matches the pinned binary at micro-memory offset `0x2800`. This proves snapshot values and overlay residency at pause, not the packet currently in flight or its object-specific TOP-relative input.

The packet source closes several GS settings beyond the earlier report. For a header pointer, `FUN_0021bc18` reads the third ushort (`param_2[2]`, header byte offset +4). `0xffff` is the no-texture sentinel; otherwise the value indexes a 32-bit pointer table at the runtime car object offset `+0xec`. `FUN_001288b0` passes the selected pointer to `FUN_001297b8` while preparing the second geometry group. This is a direct header-index-to-runtime-texture-object-table path. The race94 object join ties a live COBRA pointer table to its source model. Each of the 21 serialized texture level-zero planes occurs byte-for-byte in EE memory. All 326 COBRA headers use valid source indices except 12 sentinel headers, and all non-sentinel indices fall within the 21-record range. Thus header index → object pointer-table slot → same-index serialized record and EE-resident source bytes is closed for COBRA. A particular geometry header's draw and actual GS texture binding still are not joined.

`FUN_00128e88` builds the GIFtag primitive value as `0x4c` when the texture pointer is null and `0x5c` when it is non-null. Both specify triangle-strip primitive type and set ABE; only the non-null case sets TME. The tag's register descriptor word is `0x412` (three entries with codes 2, 1, and 4). The resumed VU code stores each output vertex as qwords `vf13`, `vf14`, and `vf12`; assigning those qwords to the descriptor sequence is not claimed here because the source-to-XGKICK/GIF-order join still needs validation.

The two `FUN_001297b8` call forms write `ALPHA_1=0x2a` for the first group and `ALPHA_1=0x48` for the second. With ABE enabled, their GS selector fields decode to `(0-0)*FIX+Cs` (source color) and `(Cs-0)*As+Cd` respectively. For a non-null texture pointer the helper also writes a dynamic `TEX0_1`, `TEX1_1=0x60`, and `TEXFLUSH=0`. `TEX1_1=0x60` sets MMAG=1 and MMIN=1 (linear selectors) with MXL=0. These are exact per-helper packet values and decoding of their fields; they do not establish that no later GS state changes intervene before every actual draw. The pinned register definitions and minimal excerpts are in [gs-register-sources.json](evidence/packet-continuation/gs-register-sources.json), drawn from [PS2SDK `gif_tags.h`](https://github.com/ps2dev/ps2sdk/blob/ac92a9f657d2e531dd8f060250b07f2a5ac6dea5/common/include/gif_tags.h), [PS2SDK `libgs.h`](https://github.com/ps2dev/ps2sdk/blob/ac92a9f657d2e531dd8f060250b07f2a5ac6dea5/ee/libgs/include/libgs.h), and [PCSX2 `GSRegs.h`](https://github.com/PCSX2/pcsx2/blob/81526d4dc7cc70e4ae75abb35a789417456c6d43/pcsx2/GS/GSRegs.h). [The exact bit-decode screen](evidence/packet-continuation/jev/jev-verify-exact-gs-bit-decodes.json) checked PRIM, both ALPHA equations, linear TEX1 selectors, and the still-open association between GIF descriptor and VU output qwords.

## One-frame executed GIF/GS evidence

The user supplied a compressed one-frame PCSX2 GSDump captured in the red-Mustang-visible race scene. The decoder in [trace_car_packets.py](../tools/trace_car_packets.py) parses the pinned GSDump record structure through exact EOF, then reads packed GIF tags and packed A+D records. The raw capture SHA-256, GSDump header and record counts, all parsed transfer counts, GS state values and limits are in [race94-trace.json](evidence/packet-continuation/race94-trace.json). Its PNG companion is the emulator window screenshot; the GSDump also contains a separate embedded 640x480 screenshot.

There are 5,879 packed geometry GIF tags with descriptor nibbles `[2,1,4]`. In pinned PCSX2 `GSRegs.h`, these mean STQ, RGBAQ, XYZF2. Its `GIFPacked STQRGBAXYZF2` consumer reads three qwords per vertex in that order, and its XYZF2 handler forwards `XYZF2.Skip()` to `VertexKick`. That closes the GIF register ordering and GS consumer semantics. The STQ qword carries S,T,Q floats; RGBAQ carries the packed color; XYZF2 carries X/Y as 12.4 screen coordinates, Z24, F8 and ADC. Source: [PCSX2 GSRegs.h at pinned commit](https://github.com/PCSX2/pcsx2/blob/81526d4dc7cc70e4ae75abb35a789417456c6d43/pcsx2/GS/GSRegs.h#L979-L1009), [PCSX2 GSState.cpp packed vertex consumer](https://github.com/PCSX2/pcsx2/blob/81526d4dc7cc70e4ae75abb35a789417456c6d43/pcsx2/GS/GSState.cpp#L1385-L1414).

Across the whole captured frame, those packets contain 135,032 vertices: 67,433 XYZF2 ADC bits set and 67,599 clear. PCSX2 defines ADC as bit 15 of XYZF2 U32[3] and passes `Skip()` into the vertex kick path. Triangle strips (PRIM type 4) occur in 2,799 tags and fans (type 5) in 3,080 tags, despite the static CPU helper building strip tags. The VU/GIF tag stream therefore can alter primitive type or includes additional producers. This is a concrete unresolved disagreement between static helper construction and the full-frame dump; it must not be papered over by treating every tag as the direct output of that one helper. The decoded aggregate topology accounts for 119,793 strip triangles and 3,481 fan triangles using each tag's NLOOP. This derives packet primitive topology, but not original source index orientation or vehicle-specific winding. The GS path has no vertex index buffer here: the order is the submitted vertex sequence, and strip/fan connectivity follows the GIF primitive type.

The candidate COBRA texture-index-0 source plane has a direct upload-to-draw interval in this dump. Source `COBRA512` mip0 (131,072 bytes, SHA-256 `6e233a…`) is an exact byte substring of IMAGE transfer 5448; its prior BITBLTBUF specifies DBP `0x36e0`, DBW 4, PSMCT32, and TRXREG 256×128. The race94 COBRA object texture pointer table slot 0 points to an object whose unsigned16 at +4 is `0x36e0`; the serialized source row is also index 0. The matching full-size TEX0 is `0x20071c06253236e0` (TBP0 `0x36e0`, PSMT8, texture size exponents 9×8, CLUT base `0x38e0`) and TEX1 is `0x60` (linear magnification/minification selectors, MXL 0). Treat that upload's lifetime carefully: the first subsequent IMAGE packet whose start DBP enters the upload-payload span estimate is transfer 6273, so the transfer-5448→6273 lifetime bound is approximate rather than a complete GS page-alias proof. The same TBP0 has earlier smaller-dimension/other-CLUT alias draws and is also present in other loaded cars' runtime texture objects; TBP0 alone is not a car identity.

There are 106 geometry tags using the full-size TEX0 between upload 5448 and that candidate overwrite. Every tag is triangle strip with PRIM `0x1c` (TME=1, ABE=0), TEX1=`0x60`, and ALPHA1=`0x44`. Thus the actual stream confirms the source texture's transfer address and filtering selector in this bounded interval; alpha blending is disabled by PRIM ABE=0 even though ALPHA1 is written. The runtime PRIM ABE bit differs from the source CPU helper's constructed `0x5c` tag, so the helper's material value alone is not the executed state.

The source-header UV join is exact for 105 of those 106 tags. For each match, packet STQ `S/Q,T/Q` agrees in vertex order to a COBRA header with source texture index 0 and its signed16 two-component source plane divided by 2048, with maximum absolute error below `1e-6`. Sixty matching tags have one exact header candidate; 45 have multiple candidates because distinct header records reuse identical UV planes; one seven-vertex tag has no exact candidate. The first three unique cases are transfers 5454, 5460, and 5466, matching source headers 0, 1, and 2. A copied source U value perturbed by one unit is rejected in every one of the 105 cases (expected delta `1/2048`). As a negative control, the first-eight-vertex comparisons reject all comparable index-0 source headers for the five other joined models; this is a prefix-only exclusion. These results strongly connect the COBRA index-0 source UV stream to the packets in this upload lifetime without resolving duplicate header identities or every vertex of the cross-car controls. Full per-tag candidates and error values are retained in [race94-trace.json](evidence/packet-continuation/race94-trace.json), with a compact disposition in `source_packet_match_summary`.

ADC is now interpreted more precisely. In pinned PCSX2 `VertexKick`, a nonzero XYZF2 `Skip()` still appends the vertex buffer record, then the triangle-strip path advances its head and returns before adding a triangle index kick; in effect that kick does not emit the triangle it would otherwise complete. For the unique UV-header subset only (ambiguous header candidates excluded), source four-byte lane 3 bit 0 versus emitted ADC yields 1,297 source0/ADC0, 1,138 source0/ADC1, zero source1/ADC0, and 1,143 source1/ADC1 vertices. Comparing each vertex's would-be current strip triangle in emitted signed 12.4 screen XY shows negative signed area in 1,132 of the 1,138 extra source0/ADC1 cases (one zero, five positive); among source0/ADC0, only 3/1,297 are negative. Source-local V3-16 XY is less decisive for the same source0/ADC1 cases (824 negative, 130 zero, 184 positive). This strong post-transform correlation fits extra skip bits on negative projected triangles, but does not by itself prove the VU's decision rule or establish a complete backface-culling implementation.

The saved overlay-5 code groups four projected vertices, applies `clipw.xyz` to each, checks clip flags with `fcand` masks `0x28a28a` and `0x145145`, and has nonzero branches that skip the nearby packet-store/XGKICK path to the loop test. This proves there are clip-gated packet paths, but the masks and this capture do not prove that the ADC correlation comes from those clip branches. In the supported unique-header subset, no source flag 1→ADC0 case occurred; source flag 0→ADC1 aligns with the negative projected triangle pattern. Keep the source W/lane-to-ADC transform as an empirical correlation, with its exact VU condition still open. Raw pair counts, all per-tag candidates, and signed-area control totals are retained in [race94-trace.json](evidence/packet-continuation/race94-trace.json); the VU instructions are source-pinned in [static-trace.json](evidence/packet-continuation/static-trace.json). ## Seven-vertex untextured blended material

The one UV-unmatched packet in the bounded COBRA upload interval is GIF transfer 5906. It has seven RGBAQ vertices, each `[0,0,0,102]`, PRIM `0x4c` (triangle strip, TME clear, ABE set), and ALPHA_1 `0x44`, which selects `(Cs-Cd)*As+Cd`. Two COBRA headers with count 7 and flags `0xc01a` carry base-color word `0x66000000`, decoded by the packet's RGBA lane order to black RGB/alpha 102. They have the same six-byte signed16 XYZ plane hash and all seven positions. An affine fit from either ordered source plane to packet screen XY has maximum residual `0.186` in GS 12.4 units. This strongly binds the packet to the duplicate source geometry/material candidates; it leaves the exact header ID and semantic part name unresolved.

Raw `0021bc18` instructions make the material color mask explicit: PEXTLB/PEXTLH/PEXEWs at `0x21bc64/6c/70` permute the packed color, `vmulx.xyz` at `0x21bc8c` is selected when header bit 0 is set, and `vmulx.w` at `0x21bcb4` is selected when that bit is clear. Since `0xc01a` has bit 0 clear, this material takes the W-only scaling arm; reading typed `_vmulbc` as an all-lane multiply would be wrong. The source scales W by `DAT_70003560*FLOAT_0028f1e8`; its runtime multiplier and producer-to-packet call are not captured. The matching alpha byte is consistent with the source W byte, but it does not establish the exact opacity factor. GS blend state confirms source alpha participates; perceived final opacity was not measured.

The source exposes two related but distinct PRIM construction paths. `00128e88` emits `0x4c` for a null texture pointer and `0x5c` for a non-null pointer, so its untextured ABE setting is unconditional and independent of the opacity global. `0021bb48` instead chooses `0x4c` only when effective flag bit `0x2` is set and adds TME independently when its texture-object argument is nonzero. In `0021bf28`, source header bit 0 maps to effective flag `0x20`, bit 2 to `0x1`, bit 3 to `0x40`, and bit 4 to `0x80`; source header bit 1 is not directly mapped to the ABE flag. Effective bit `0x2` may come from the caller's nonzero third argument or from `DAT_70003560 != 1.0`. A third helper, `0021c3e0`, chooses ALPHA `0x44` in the direct untextured branch when effective bit `0x20` is clear and passes it to `0021ba50`. **Correction (2026-10-05):** `0021ba50` does not write PRIM. Its fixed `0x4c` is the A+D register *address* of FRAME_1; it writes one GIF A+D packet of FRAME_1 (`0x4c`), ALPHA_1 (`0x42`, data = that argument) and TEST_1 (`0x47`). See [Retained display-list continuation](#retained-display-list-continuation-2026-10-05); the earlier wording is superseded.

In race94, the exact COBRA node record has bit `0x10000` clear, the first `0021d180` call site passes third argument zero, the saved scratchpad's `DAT_70003560` at `0x70003560` is `1.0`, and the `c01a` header bit 0 is clear. If this direct `0021c3e0` path runs with no texture pointer, these conditions are compatible with `0021c3e0` selecting ALPHA `0x44` for `0021ba50` (superseded wording: it was previously described as a fixed PRIM/ALPHA pair; PRIM `0x4c` comes from the GIF tag built by `0021bb48`). The paused state's renderer count at `0x70003590` is zero, and the GSDump is a separate capture; this remains a source-compatible explanation, not an executed producer-to-transfer proof. The raw source checks and runtime values are recorded in [static-trace.json](evidence/packet-continuation/static-trace.json) and the `runtime_source_branch_join` / `unmatched_seven_vertex_blended_material_join` records in [race94-trace.json](evidence/packet-continuation/race94-trace.json).

The new source-header exporter and GLB validator were independently checked against raw bytes. Both scripts ran successfully; an independent pass recomputed field ownership, base-color word, RGBA lane order, scaling mask, and offset coverage for all 12,080 headers, then confirmed every source header offset appears exactly once across the 35 current GLBs. No parser/export mismatches were found. ## VU1 pass 4 and pass 5 handlers (2026-10-05, static)

[`tools/verify_vu_pass_handlers.py`](../tools/verify_vu_pass_handlers.py) decodes the handlers that the jump table reaches for pass words 4 (overlay 2 pair 46) and 5 (overlay 1 pair 213) and writes [`handlers-pass4-pass5.json`](evidence/vu-dispatch/handlers-pass4-pass5.json). [`tools/vu1_decode.py`](../tools/vu1_decode.py) decodes the overlay bytes from the VU1 instruction layout; it agrees with the pinned disassembly on all 1,558 pairs (`python3 tools/test_vu1_decode.py`). [`tools/vu1_exec.py`](../tools/vu1_exec.py) runs the dispatch, one prologue, one loop iteration and the tail with symbolic values, so the receipt holds formulas, not numbers. Evaluating those formulas numerically matches a run of the same code in the numeric domain (1,920 values per handler from 40 random inputs), and 9 mutated inputs are rejected. Nothing was executed on the game or an emulator.

- **Shared structure.** Both handlers loop over four vertices per iteration (three output qwords per vertex, 12 per iteration), copy the GIF tag from `TOP[2]` to the output buffer, set bit 0 of `DM[59].y`, kick a static VU address (`0x25` for pass 4, `0x1c` for pass 5) and branch to one epilogue at pair 758. The epilogue stores `0x2fe` at `DM[59].w` and tests flag `0x100` of `vi13`: when it is clear it kicks the output buffer and the program stops at pair 766 (E bit), and the next MSCNT continues at pair 768, which branches back to the dispatch `xtop` at pair 60; when it is set the epilogue branches to pair 797 instead, a clip stage that was not decoded.
- **Copied lanes.** In both handlers the XYZF2 qword of every vertex, and the Q and w lanes of the STQ qword, are copied unchanged from the previous output buffer. The handlers do not compute ADC; any ADC bit in their output comes from the pass that wrote that buffer.
- **Pass 4.** With `V = (position − DM[7]) · position.w`, `d = V · N` (N is the normal plane), the handler reflects V about N, negates the result (R) and transforms it by the matrix held in the three qwords `TOP[12]`–`TOP[14]` (`x′ = TOP[12].x·R.x + TOP[13].x·R.y + TOP[14].x·R.z`, and likewise for `y′` and `z′`). The texture coordinates are `0.5 · x′/(−1 − |z′|) + 0.5` and `−0.5 · y′/(−1 − |z′|) + 0.5` times the previous Q, a paraboloid-style environment mapping. RGB is `ftoi0(colour.xyz · min(1 + 0.95 d, 1))`. The RGBA w lane receives `min(1 + 0.95 d, 1)` as an unconverted float.
- **Pass 5.** RGBA is the same for every vertex of a draw: `ftoi0(min(DM[5].xyz · colour.xyz, 128))` with alpha `ftoi0(min(DM[5].w, 128))`. The texture coordinates are `t = colour.w · Q` and `s = max(0.5 · ((R + V) · V) − 0.5, 0) · Q`, where `R = 2(N · DM[6])N − DM[6]` and `V = (DM[7] − position) · position.w`, a specular-style intensity.
- **What this does and does not say.** The formulas are exact statements about the microcode; the names (environment mapping, specular) are a reading of the arithmetic. For the open question about the RGB of passes 4 and 5 this gives a formula-level answer: pass 4 scales the header colour by a per-vertex factor of at most 1, pass 5 uses a per-draw constant. The pass 4 alpha lane holds the factor's float bits and the packed-RGBA consumer reads the low byte of each 32-bit lane, so a per-vertex varying alpha is expected there; the captured float factor predicts RGB on all 37 compared pass-4 draws. The retained matrix packets now supply `DM[5]`–`DM[7]` and `TOP[12]`–`TOP[14]` for the bounded comparison in [VU handler dump comparison](vu-handler-dump.md). Still open: reconstructing the pass-4 factor from position/plane inputs, full S/UV reconstruction, the producer of the static kick packets, the pass 1 and 2 handlers that write the buffers these handlers copy from, and the clip stage at pair 797.
