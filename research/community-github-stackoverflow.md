# Community research: GitHub and Stack Overflow leads for PS2 car recovery

Research pass: 2026-10-04. Scope: GitHub extractor/source repositories and Stack Overflow threads with code-level relevance to recovering original PS2 vehicle meshes and textures, interpreting VIF/VU/DMA/GIF/GS streams, and getting clean DCC exports. Searches targeted Ford Racing 2, `SLUS-20788`, Razorworks, VIF unpack, CLUT/swizzle, UVs and Blender export.

## Finding for Ford Racing 2

I did not find a public GitHub or Stack Overflow extractor specifically for Ford Racing 2's PS2 cars in the searches listed below. This is a bounded search result, not proof that no private, unindexed, deleted, or forum-only work exists. The most useful material is source code for other PS2 games. Treat it as a way to form experiments against the existing FR2 files, never as evidence that FR2 shares the same record layout.

The strongest next experiment is to parse FR2's DMA/VIF/GIF commands with explicit state and compare the resulting candidate geometry against the current compact records. ## Most useful GitHub source: Road Trip Adventure / ChoroQ

Matthew Holey's [`roadtrip-choroq-tools` README](https://github.com/mholeys/roadtrip-choroq-tools) says the PS2 game stores pre-prepared rendering commands and tags; files are transferred to GS/VU1, and texture-to-mesh association is represented through GIF tags. The author credits older Xentax mesh and Zenhax texture discussions, and says much of the implementation was later rewritten after recognizing that the game contains raw PS2 command/tag streams. This is a useful research trail: [Xentax thread `t=17567`](https://forum.xentax.com/viewtopic.php?t=17567) and [archived Zenhax thread `t=7405`](https://web.archive.org/web/20220309142950/https://zenhax.com/viewtopic.php?t=7405).

The [`car.py` implementation](https://github.com/mholeys/roadtrip-choroq-tools/blob/master/choroq/egame/car.py#L1433) documents its own format as little-endian, with nested offsets leading into mesh data. The parser walks DMA tags and VIF commands, keeps VIF state, collects expanded VIF payloads, and parses GIF packets when a VU1 execution address matches the game's known car routines. It uses GIF register descriptors `ST`, `RGBAQ`, and `XYZF2` to identify a vertex packet, then reads position, normal, color, a texture-coordinate tuple, and additional fields. The source treats the third texture tuple component as uncertain and notes that other fields may relate to color selection or shading. Those labels and execution addresses belong to ChoroQ and must be rediscovered for FR2.

That parser does not read triangle indices from a conventional index buffer. Its inherited [`AMesh.create_face_list`](https://github.com/mholeys/roadtrip-choroq-tools/blob/master/choroq/egame/amesh.py#L517) synthesizes faces from sequential vertices and alternates winding, consistent with a triangle-strip interpretation. The method credits a forum script. For FR2, inspect GIF `PRIM` primitive type and strip/fan/list indicators, including restart/ADC behavior, before using any strip hypothesis; the ChoroQ face rule is not transferable evidence.

One especially relevant limitation is visible in the same project's [`ps2_utils.py`](https://github.com/mholeys/roadtrip-choroq-tools/blob/master/choroq/ps2_utils.py#L2960): it advertises VIF `UNPACK` variants but explicitly exits for compact `V2-16`, `V3-16`, `V4-16`, and other variants. Since the current FR2 analysis reports 6-byte V3-16, 4-byte V4-8, and optional 4-byte V2-16 records, this extractor cannot directly decode all the formats under investigation. Use it as a reference for command sequencing and state organization; implement compact unpack semantics from a more complete PS2 implementation/specification and validate sign extension, scaling, VIF cycle/mask modes, and end padding against FR2 bytes.

The project's [`car_extractor.py`](https://github.com/mholeys/roadtrip-choroq-tools/blob/master/car_extractor.py#L564) demonstrates the complete artifact path: parse the car, associate textures and palettes, export each mesh section, and write OBJ/PLY plus material data. It preserves named parts such as body, lights, spoiler and stickers. The project texture helper [`texture.py`](https://github.com/mholeys/roadtrip-choroq-tools/blob/master/choroq/egame/texture.py#L1187) reads texture DMA/GIF data and GS state; the car export path unswizzles a CLUT before assigning it to an indexed texture and writing PNG. Its swizzle routines are game-specific, so use the key lesson—decode the CLUT through the same GS state as the texture—rather than copying the permutation.

## Other useful GitHub implementations

[`mattbruv/rumble-racing-re`](https://github.com/mattbruv/rumble-racing-re) is a PS2 game-specific reverse-engineering project with a reproducible disc-file-to-asset pipeline. Its README states that it reads original `.AV`/`.TRK` files, writes textures as PNG, and exports 3D maps as glTF for Blender. This is a practical format target for FR2 validation: a car asset should reopen with its materials and texture references intact. It focuses on maps rather than cars, so it does not identify FR2's vertex layout.

[`BlackLineInteractive/Climax_Game_Engine_Toolkit`](https://github.com/BlackLineInteractive/Climax_Game_Engine_Toolkit/blob/master/docs/formats/SH_FORMAT.md) gives another example of the command-stream approach for a different PS2 title: its geometry reader walks RenderWare structure and VIF1 display lists, which upload data to VU1. This independently supports examining the command stream around candidate vertex blocks instead of assuming every compact record is a standalone vertex array. It is a different game and does not define FR2's commands.

For lower-level cross-checks, the [PS2SDK VIF packet API](https://ps2dev.github.io/ps2sdk/group__packet2__vif.html) describes VIF unpack parameters, including the destination VU address and signed/masked choices. PCSX2's [VIF implementation](https://github.com/PCSX2/pcsx2/blob/master/pcsx2/Vif.cpp) is a further implementation reference. The old ChoroQ utility is a useful worked extractor but not the authority for VIF edge cases.

## Stack Overflow: useful export constraints, no FR2 format evidence

The search did not surface a Stack Overflow post that explains FR2, PS2 VIF, GS texture swizzling, or PS2 model extraction. The useful results instead describe common mesh-export pitfalls:

- In [“how to export per-vertex UV coordinates in Blender export script”](https://stackoverflow.com/questions/13327379/how-to-export-per-vertex-uv-coordinates-in-blender-export-script), the accepted answer explains that one geometric vertex can have different UV values on different face corners. A flattened OBJ/glTF/VBO export must retain per-corner UVs, usually by duplicating vertices at seams. This matters when recovered FR2 UVs appear inconsistent under a one-UV-per-position representation.
- [“Trouble loading simple mesh into OpenGL”](https://stackoverflow.com/questions/28260272/trouble-loading-simple-mesh-into-opengl) illustrates that an importer must either provide positions, normals, UVs and connectivity or handle missing attributes. It is generic troubleshooting, not a PS2-specific format source.
- Blender mesh loops also expose corner data such as tangents in [“How to export tangent data of a 3d model from blender”](https://stackoverflow.com/questions/36214962/how-to-export-tangent-data-of-a-3d-model-from-blender). This is useful only if FR2's optional records turn out to carry tangent-like data; the title-specific ChoroQ source does not prove that interpretation.

These community Q&A posts are low-authority supporting references. The project's own binary evidence and Blender's current data model should decide the export representation.

## Suggested FR2 experiments

1. Preserve raw packet evidence per car: offsets, DMA tag fields and boundaries, VIF command words and state (`STCYCL`, `STMOD`, `STMASK`, `STROW`, `STCOL`, `BASE`/`OFFSET`), unpack format/count, expanded payload length, and following GIF tag/register descriptors. This mirrors the successful separation of VIF and GIF state in the ChoroQ source without inheriting its game-specific values.
2. For the observed 6-byte/4-byte streams, implement candidate VIF unpack transforms (signed and unsigned compact fields, including 5-bit formats only if observed) from PS2 references. Record both raw integers and normalized values. Compare count × stride calculations against packet lengths and alignment/padding, and reject candidates that overrun or leave unexplained payload bytes.
3. Determine topology from GIF `PRIM` and packet boundaries. Render independent hypotheses (triangle strip with alternating winding, triangle list, and any primitive indicated by the tag) for one simple car part and compare silhouettes and face normals. Keep UV/color/normal streams attached to face corners while testing.
4. Trace texture state separately: parse GIF register writes and image payloads; connect the texture's TBP/TBW/PSM and CLUT/TEX0/TEXCLUT state before applying GS address swizzle rules. Save raw indexed pixels, raw CLUT bytes, and decoded output side by side. The ChoroQ code demonstrates the need for texture-specific palette handling but its ordering formula is not an FR2 answer.
5. Export a tiny representative car to glTF (or OBJ+MTL) with each corner's position/normal/UV tuple preserved, plus separate meshes/materials for body, wheels, glass, lights and shadows when the packets support those separations. Re-import into Blender and compare against an in-game/emulator capture; do not merge attributes solely by position.
