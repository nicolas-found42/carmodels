# Original car PTG and texture recovery status

## Answer

The car icon/livery `.ptg;1` files are not currently decoded to complete faithful images. The current PTG checker validates their common 32-byte header and classifies every car PTG as `tiled_header_only`; its exact body decoder applies only to a different 0xDD-filled tiled profile, and its rendered sprite decoder applies only to one-tile assets. A fresh read-only pass over the car reference corpus found 171 PTGs, all 100,304 bytes: 35 menu icons with header dimensions 165×98 and 136 livery files with dimensions 227×85. All have 24 tiles and a 32-pixel cell, arranged 6×4 for icons and 8×3 for liveries. These are header dimensions and tile-grid facts; they do not establish a complete decoded image, palette, or pixel orientation. [The PTG profile implementation](../../../reverse-engineering/tools/ptg_profile.py) [and its verifier](../../../reverse-engineering/tools/verify_ptg.py) make this limit explicit.

The broader texture work has recovered level-zero decoding for textures embedded inside the `.PS2;1` model containers. It does not decode the separate car `.ptg;1` icon/livery assets. In the unchanged PAL model corpus, the parser found 2,370 embedded images across 56 models: 350 format 1, 1,551 format 3, and 469 format 4. The bounded decoder emits level-zero RGBA for formats 1, 3, and 4, and the independent index-plane check covers all 2,020 indexed images. Mip pixels and live rendering remain outside that result. [The model texture parser](../../../reverse-engineering/tools/ps2_container.py), [index decoder](../../../reverse-engineering/tools/ps2_texture_indices.py), [corpus result](../../../reverse-engineering/notes/evidence/fr2-texture-upload-audit/rgba-corpus-result.json), and [audit notes](../../../reverse-engineering/notes/evidence/fr2-texture-upload-audit/README.md) document the implementation and limits.

## What the car PTG experiment established

I ran the repository's existing `ptg_profile.classify` implementation against every `.ptg;1` in `projects/carmodels/reference/ford/cars`, then separately compared icon and livery files sharing a code for four cars. The experiment and its complete per-file hashes and header results are saved in [the car PTG profile output](evidence/ptg-investigation/ptg-profile-carmodels.json) and [byte inventory](evidence/ptg-investigation/carmodels-ptg-byte-inventory.json).

The measured eight-word little-endian header is `[count, columns, rows, stride, cell, width, height, last]`. All 171 car files satisfy the repository's checked relations: `count = columns × rows`, `stride = cell = 32`, `columns = ceil(width / 32)`, and `rows = ceil(height / 32)`. Each count is 24. The icon/livery header dimensions divide into 35 at 165×98 (6×4 cells) and 136 at 227×85 (8×3 cells). Every header's last word is 1, so none matches the `0xDDDDDDDD`-trailer layout that the existing multi-tile body checker understands. [The profile code](../../../reverse-engineering/tools/ptg_profile.py) defines that exact supported layout and deliberately labels other multi-tile bodies header-only.

The four equal-code pairs (`torinod`, `f15004d`, `tbirdd`, `fr200d`) are distinct files, not duplicate copies: each icon has the common 165×98 header, each livery has 227×85, and 63,955–67,593 bytes differ in each pair. For example, the Gran Torino icon and `torinod` livery each occupy 100,304 bytes but differ at 64,063 byte offsets. This shows the shared code is useful for associating a menu icon with its default livery choice; it does not mean their binary pixels or dimensions are interchangeable. Exact hashes and offsets are recorded in the experiment artifact. The per-car manifest preserves source archive paths, destination roles, file sizes, and hashes; [Gran Torino's manifest](../reference/ford/cars/GRAN_TORINO/manifest.json) is one example.

Prior corpus work on 548 disc PTGs measured the same universal header relations. For the 17 files whose final word is `0xDDDDDDDD`, it also established a precise `1120 + 1104 × tile_count` byte layout, 16-byte pointer records, 64-byte descriptors, and a 1,024-byte-per-tile pixel span. Those pointer values were outside the file and their meanings were unresolved; palette location and descriptor semantics were unresolved too. Those 17 are not the car PTGs, whose final header word is 1. [The source-backed PTG findings](../../../reverse-engineering/notes/evidence/fr2-continuation/jev/d012b-verify-ptg-header-size-with-source.json) and [decision evidence](../../../reverse-engineering/notes/evidence/fr2-continuation/jev/d011-decide-ptg-next.json) preserve the underlying measurements and uncertainty.

The existing single-tile renderer is narrower still: it requires `count == 1`, a 32-pixel cell, a specific 1,024-byte pattern table, and padded linear rows. It was used for eight gear sprites. Thus its grayscale PNG output is not a decoder for the multi-tile car icons or liveries. [The single-sprite contract](../../../reverse-engineering/tools/format_contracts.py) and [renderer](../../../reverse-engineering/tools/ptg_render.py) show those preconditions.

## Relation to the car model's embedded textures

The model container has its own texture library: palette block counts and entries, named texture descriptors, dimensions, format/mip fields, then image planes. Its names include car body maps such as `GRAN_TORINO_512`, `GRAN_TORINO_256`, `GRAN_TORINO_128`, and `GRAN_TORINO_64`, plus `GRAN_TORINO_MOVING_WHEEL` and `UNDER_SHADOW`. The saved corpus result reports six embedded Gran Torino textures (five format 3 and one format 1) and their dimensions, mip counts, palette references, offsets, and decoded level-zero RGBA hashes. [Gran Torino's model result](../../../reverse-engineering/notes/evidence/fr2-texture-upload-audit/rgba-corpus-result.json) provides a concrete record; [the section parser](../../../reverse-engineering/tools/ps2_container.py) describes where those structures are read.

The reference tree separately retains `GRAPHICS/GAME/CARS/<code>.ptg;1` menu icons and `GRAPHICS/GAME/LIVERY/<code>.ptg;1` livery files. The files with the same code are not byte-identical, and the embedded texture parser consumes `.PS2;1` model containers, not those PTGs. Therefore the recovered embedded RGBA maps should not yet be presented as decoded versions of the livery PTGs, nor does a texture name alone prove which model UV/material uses it. [The reference layout](../reference/ford/README.md) and [asset-building source](../tools/build_reference.py) show the separate source directories and name-based association.

## Original mesh recovery lead

The per-car model parser and static trace work have also narrowed the mesh problem but have not recovered original renderable car meshes. The corrected geometry-section audit maps serialized geometry records and variable payload spans, yet explicitly leaves those payloads unnamed: it has not shown they are positions, indices, normals, or a complete VIF/VU1 draw stream. A separate trace ties some serialized object-row floats to a VU0 transform input, but does not establish renderer submission. [The corrected geometry consumer audit](../../../reverse-engineering/notes/evidence/fr2-geometry-consumer-audit/README.md) and [object-row provenance](../../../reverse-engineering/notes/evidence/fr2-geometry-consumer-audit/object-float-provenance-01.md) state these boundaries.

## Recommended next evidence to collect

1. Trace the executable's multi-tile PTG consumer from file load through its pointer records/descriptors to the GS upload registers. Record the exact instructions and source spans that establish each pointer's base, descriptor fields, pixel dimensions, tile order, and palette source. The older PTG evidence specifically identifies pointer meaning and palette location as open.
2. Recover one car PTG end-to-end first (for example Gran Torino's icon and default livery), then compare the resulting pixel image against a ground-truth in-game or emulator texture capture. Keep the icon and livery as separate assets in that comparison because their bytes and header dimensions differ.
3. For model textures, continue from the existing `.PS2;1` level-zero decoder to controlled mip interpretation and establish name-to-material/UV use. The current static contract proves byte layouts and bounded index/RGBA outputs, not renderer selection or UV assignment.
4. For meshes, trace one specific geometry payload plane from loader cursor to a direct consumer and then through the VIF/VU1 packet path. Do not label serialized planes as vertex/index data until that path identifies their semantics.

The strongest current practical output is therefore: original model texture level-zero pixels are available for the bounded formats; original car PTG icon/livery headers, dimensions, and associations are mapped; complete car PTG pixels, palette, tile permutation, mip handling, and original renderable meshes remain open.
